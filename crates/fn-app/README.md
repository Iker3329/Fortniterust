# fn-app: `fortnite-rs`, the pure-Rust game binary

winit 0.30 window + wgpu (`fn-render` scene, `fn-ui-wgpu` UI) + gilrs gamepad, driving `fn_game::GameSim`. No C/C++ dependency; `unsafe_code = "deny"` in this crate with ONE opt-out module, `src/sys.rs` (a handful of Win32 calls through the `windows-sys` bindings crate: message box, console attach, cursor clip read-back, monitor work area; a test fails if `unsafe` appears in any other file).

```text
cargo build -p fn-app --release          # -> target\release\fortnite-rs.exe  (keep it beside an `assets` folder, or pass --assets)
fortnite-rs                              splash -> loading screen -> world; settings from FortniteSettings.ini beside the exe
fortnite-rs --assets <dir>               exported asset tree (default search: --assets, env FN_ASSETS, then `assets` beside the exe; no baked-in developer paths. Nothing found -> native message box listing every place looked at, exit 1)
fortnite-rs --paks <Paks|install dir>    meshes + animations decoded straight from the paks (fn-pak/fn-mesh/fn-anim through fn-pose)
fortnite-rs --smoke-test --out <dir>     fixed-60 Hz walk/jump/crouch/sprint/swing run, 14 captures, frame log, perf report, fn-sim diff
fortnite-rs --script <file|builtin:smoke|walk|pickaxe> [--compare-sim] [--out dir] [--size WxH] [--frames N] [--vsync]
fortnite-rs --screenshot out.png [--size WxH]
fortnite-rs --live-test --out <dir>      interactive path self-test (see Verification); FN_TRACE=1 prints window events
```
Script format: see `src/script.rs` (ranges of held actions, `shot name`, `resize WxH`, `equip`, `yaw=`, `props sandbox|none|tree|real|realtree|realrock`). `--props real|sandbox|none`, `--prop-radius M`: see "Real 1.8 props".

## Architecture
| module | role |
|---|---|
| `app` | `ApplicationHandler`; state machine Boot -> Splash (Splash.bmp, in-window) -> Loading -> Finishing -> Playing / Failed; per-frame loop (real dt clamped to 0.1 s, fixed 1/fps in scripts) |
| `loader` | real load steps driving the loading bar: mount paks, models, one step per clip (decoded on worker threads), ground texture, HUD/menu art + GPU warm-up, pickaxe, renderer ("Compiling shaders") |
| `assets` | ordered asset roots found by file name; pak detection (`fn-pak` probe); `fn-export --md5` cache fallback |
| `input`, `keys` | key/mouse state, the old focus + capture policy (`fn_game::host`), `FrameInput` from the user's bindings, raw-mouse look, gamepad merge |
| `platform` | `PlatformHost` over winit: windowed (centred in the real monitor work area) / borderless / exclusive fullscreen (video modes, cached for 10 min), min client 640x360, max 8192, vsync flag, the old runtime's cursor capture policy (see below) |
| `gfx` | surface, non-sRGB format, present mode (vsync), acquire/resize; every size clamped to the device's `max_texture_dimension_2d`; wgpu errors recorded (no panic) and reported as `Acquire::Fatal` |
| `scene` | `fn_pose::CharacterRig` pose -> skin matrices -> `Renderer`; pickaxe on the RightHand socket (`MaterialKind::Prop`); the harvestables as the REAL 1.8 textured static meshes (`Renderer::set_static_instances`, see "Real 1.8 props"), or, without the exported assets, the procedural placeholders through `Renderer::set_prop_instances` |
| `props` | the real 1.8 trees / rocks / bushes: catalog + collision hulls + layout (`fn-propdata`) -> `Library` (protos, placements, `Harvestable`s with hulls), `Real` (proto -> uploaded mesh handle), `--props` / script `props real` modes |
| `diag`, `sys`, `settings_guard` | console attach + `fortnite-rs.log` + stderr tee, panic hook, native message boxes; the only `unsafe` (Win32 bindings); pre-load check / repair of `FortniteSettings.ini` |
| `backend` | `AppBackend`: `LiveVideo` + `RenderSettings` (renderer hooks), input, audio hook, atomic ini save; also the Settings screen's `ApplyBackend` |
| `ui` | splash, HUD through `fn-hud-adapter`, Esc menu / Settings (`MenuSystem::frame_with`), winit -> menu events |
| `audio`, `audio_test` | the real engine behind `fn_audio_sink::AudioSink` (`open_for_app`), `GameplayAudio` (sim state -> sound events + listener), `SinkHooks` (Settings > Audio), `--audio-test` offline render + analysis, `--audio-device-smoke` |
| `pad` | `PadBackend` over gilrs (XInput), `NoPad` |
| `script`, `run`, `stats` | scripted input timelines, capture + log + report, p50/p95/p99 |

## Cursor capture (the old runtime's `lock_mouse` / `release_mouse`, `platform.rs`)
Capture: refused unless the window is focused AND the OS foreground window AND not minimised; the cursor is moved to the client centre FIRST (`set_cursor_position`), then grabbed (winit `Confined`, `Locked` as fallback; on Windows winit turns a hidden Confined grab into a 1x1 `ClipCursor` at the client centre it computes itself, `Locked` into a 1x1 clip at wherever the pointer is at that instant, which is why the old order "Locked first, centre afterwards" pinned the pointer outside the window); the cursor is hidden ONLY after a grab succeeded and the real clip rectangle was read back (`GetClipCursor`) and found to be a tiny box inside the client area (else undone and the next mode is tried); a failed capture leaves the mouse free and visible and retries after 750 ms. Release (Esc menu, focus loss, minimise, alt-tab, exit) is unconditional: `set_cursor_grab(None)` + `ClipCursor(NULL)` (winit skips its own release while the window is unfocused) + show cursor. Look uses raw `DeviceEvent::MouseMotion`; the per-frame `recenter()` only acts when the pointer is not already at the centre. The capturing click is held back from the fire binding (`InputState::mark_captured`). Every capture / release prints a `[capture] ok|VIOLATION clip=... client=... cursor=...` line and is kept in `WinitPlatform::last_audit` (the live test log shows them: e.g. `clip=(1280, 707, 1281, 708) client=(640, 347, 1920, 1067)`; released: `clip=(0, -476, 3640, 1444)` = the whole desktop). Unit tests: order of operations against a recording mock, refusal cases, the audit verdicts, a real hidden window never captures.

## Failure UX and logging (`diag.rs`, `sys.rs`, `main.rs`)
* Release builds are GUI-subsystem (no console window on double click; debug builds stay console). Started from a terminal the exe attaches to the parent console (`AttachConsole`), or keeps redirected handles. Under PowerShell use `Start-Process -Wait -PassThru` (or pipe the output) to wait for it and read `ExitCode`.
* `fortnite-rs.log` beside the exe (temp folder when that is read-only; previous run kept as `fortnite-rs.previous.log`) gets everything written with `eprintln!` (stderr is teed through a pipe, flushed before exit) plus panics and `[slow]` diagnostics.
* Native message box (`MessageBoxW`) for: missing / incomplete assets (names the files and every place that was looked at, exit 1), a panic (location + log path, then exit 101; was a silent 0xC0000409), window / GPU creation failures (`Acquire::Fatal`, exit 1). Boxes are suppressed in automated runs (`--smoke-test`, `--script`, `--screenshot`, `--live-test`) and when `FN_NO_DIALOG` is set, so a harness never hangs; the message still goes to stderr / log. `FN_TEST_PANIC=1 fortnite-rs` exercises the panic path.
* `FortniteSettings.ini` is checked once before the app loads it (`settings_guard.rs`): a corrupt file moved to `.corrupt` is reported (`[settings] ... moved to ...corrupt`), a `Resolution` above 8192 / malformed is repaired IN THE FILE.
* Numbers that used to be silently fixed are errors: `--frames 0`, `--size` below 640x360 or above 8192, script `size` / `resize` outside that range, a script frame number of `u32::MAX`.

Policy implemented as in the old runtime: no capture while unfocused, held keys dropped on focus loss, Esc opens the menu and frees the mouse, closing it (or a click) re-captures, the capturing click does not swing, menu pauses the simulation, minimised window releases the mouse and stops rendering, Start button opens the menu on release.

## Real 1.8 props (`props.rs`; the procedural trees / rocks are now only the fallback)
Source: `<assets>/props` (`fn-export props export`: 85 kinds, 49 of them in the loaded categories tree / rock / bush / hedge; found as `<asset root>/props/catalog.json`, or `FN_PROPS_DIR`), read through `fn-propdata`; meshes + materials uploaded with `fn_render::static_loader`.
* **Loading (step-driven)**: `Loader::start` reads the catalog and builds the `props::Library` (8 ms), then only the kinds the run places are loaded (the layout's ~20 distinct kinds near the spawn, or the single test prop; all 49 would take ~4 s more). Their glTF + PNG decode runs on a pool of up to 4 threads while the renderer compiles its pipelines (bounded queue: at most 6 decoded kinds in memory), then the worker uploads them kind by kind: one progress unit `Loading prop: <id>` each (`loader::plan_with_props`), so the bar still moves only when a step completes. `fn_render::static_loader` got an additive `prepare_kind` (CPU) / `upload_prepared` (GPU) split for this (`load_catalog` is unchanged: it calls both). Measured (release, RTX 2060): load 1.4-2.1 s with the sandbox, 3.3-3.9 s with the layout (20 kinds), 2.3 s with one prop.
* **Placement** (`Library::spawn_layout`): `layout/all.json` (9609 `Athena_Terrain` placements, RECOVERED: position, yaw, uniform scale) filtered to `--prop-radius` (default 150 m, CHOSEN) around the `sample.json` centre (the harvestable with the most trees AND rocks within 40 m: an `Athena_Tree_Large_1`, RECOVERED), translated so that centre sits at `props::ANCHOR` = 22 m in front of the spawn (CHOSEN). UE world cm (left handed, Z up) -> game `(x, z, y) * 0.01`, yaw `-yaw` about +Y, as `fn-propdata` documents. **The player spawn stays where `fn_game::spawn()` puts it (0, 12) on the flat 512 m baseplate**: the 1.8 data has no player start (players drop from the battle bus) and the island terrain height is not modelled, so every prop stands on y = 0 (ASSUMED/CHOSEN). Placements within 3 m of the spawn (or whose hull is within 1.5 m of the chest point) and outside the baseplate are dropped. 308 props are placed with the defaults: 57 `Athena_Tree_Large_1`, 71 pines, 32 medium trees, 103 shrubs, 45 rocks (20 kinds).
* **Collision from the real convex hulls**: `collision.json` -> `fn-hull` rebuilds each convex (vertices only in the data) as a polytope (incremental hull; distance field, closest point, ray, sphere sweep, exact segment-vs-hull distance), baked per instance (scale, yaw, position) into `Harvestable::hull`. An oak is 9 hulls (trunk + canopy slabs up to 22 m), a pine 2, a rock 1-3. Player: `fn_movement::scene::Scene` gained `hulls` (probe / sweep / floor ray like the frusta), `Controller::hulls` is filled every tick by `GameSim::refresh_blockers` with the hulls within 6 m (`fn_props::player_hulls`); the capsule (34 cm radius, 75 cm half height: unchanged) slides, steps up and stands on them. Camera boom: `fn_props::trace` / `clearance` use the hulls. Pickaxe: `fn_combat::trace_cylinders` (also the reticle's aim test) sweeps the 20 cm sphere against the hulls; a second knee-height (35 cm, ASSUMED) sweep runs only when the chest-height one misses, because shrubs (0.6 m) and small rocks are below the chest line. Procedural placeholders keep their cylinders / frusta (a real prop has `hull = Some(..)`, possibly empty = no collision).
* **Health and resources, per kind (RECOVERED, from the catalog)**: `Harvestable::max_hp` = `health.max` (600 large oak / `Athena_Tree_Hero_02`, 450 large rocks, 300 pines 3 / 05, 200 medium trees and pine 01, 180 small rocks, 120 `Tree_04` and hedges, 30 shrubs, 50 `Prop_Rocks_StoneSmall*`); one swing still deals `HARVEST_DAMAGE` = 50 (`EnvDmgPB`, RECOVERED), so an oak takes 12 swings, a large rock 9, a shrub 1. The resource (`Wood` / `Stone`) and the catalog's `ResourceRates` / `AthenaResourceRates` rows (`ResourceWoodHigh`, `ResourceStoneHigh`, ...) are exposed on `Proto::resource` / the `[props] placed:` log; **the amount a hit awards stays the PROVISIONAL 50-per-swing rule** (= the damage), because the rows' meaning is native code. `World::wood` / `stone` (and a new `metal`) feed the HUD counters as before; `HarvestEvent::resource` is the real one.
* **Hit shake and destroy**: a hit sets `Harvestable::shake = 0.3` (the old runtime's decay) which is `StaticMeshInstance::shake` (the renderer's x-sway). At 0 hit points the prop is removed from the static list on the same frame (no instance, no collision, no further hits). **There is no stump / debris mesh in the 1.8 export** (`destruction.replacement_class` is null for every tree and rock: the actor is removed and a particle system plays, which is not ported), so the prop simply disappears. Real props do NOT regrow (ASSUMED: the real game does not respawn a destroyed tree; the 8 s regrow of the sandbox placeholders is unchanged).
* **Audio**: `Harvestable::kind` is `Rock` for the `rock` category and `Tree` for everything else (bushes and hedges sound like trees: ASSUMED, there is no separate cue), so the existing `fn_game::audio_events` hook (`p.kind` -> `HitSurface`) now sounds like a real rock or tree; tests chop a real oak (12 `Tree` hits, one destroyed) and a real large rock (9 `Rock` hits).
* **Fallback (never a panic)**: no `props` folder, an unreadable / wrong-schema catalog, an empty library, a kind that fails to decode: the procedural trees / rocks stay (whole sandbox, or per kind: a prop whose mesh did not load is drawn as the placeholder at its real position with its real hull). One `[props]` log line says which.
* **Modes**: the live game and `--screenshot` place the layout; `--props real|sandbox|none` overrides; scripts keep their own `props` line (default `sandbox`, so the parity scripts `smoke` / `walk` / `pickaxe` and their `--compare-sim` logs are unchanged and do not even load the props); new script values `props real` (layout), `props realtree` (one `Athena_Tree_Large_1` whose hull surface is 1.4 m from the pawn) and `props realrock` (one `Athena_Prop_Rocks_StoneLarge01`). `--prop-radius M` (5-250). Walking, swinging and the HUD are the normal game code.
* **Tests** (real-asset tests skip, with a note, when the export is missing): hull maths (`fn-hull`, 10), capsule / sweep / floor probe / controller against hull boxes (`fn-movement`, 4), camera + player-hull mapping (`fn-props`, 2), real-prop health / resource / no-regrow / knee sweep (`fn-combat`, 3), and in `fn-app`: UE -> game axis / scale / rotation conversion, the mesh-bounds-vs-hull frame check on every kind, the layout anchor / spawn clearance, kinds-needed, one-prop placement distance, a 2520-step walk through the real layout (no capsule penetration, 0.11 ms mean per sim step, max 1.6 ms), chopping a real oak (12 swings, 600 wood) and rock (9 swings, 450 stone) with the audio moments, every kind's hit count = ceil(hp / 50), static / procedural split, missing / broken assets.
* **Numbers** (release, RTX 2060, `--script` perf walk: sprint + turn + swings + jumps through the layout, 1615 frames, vsync off; `reports\props-in-game\perf`): see the table in `reports\props-in-game\README.txt`.
* **Not done / honest**: no terrain (props on y = 0); the pickaxe trace origin is still the pawn's chest / knee along the facing, not the camera aim; the oak canopy slabs are real hulls (a jump into the foliage is blocked by them); LOD distances, wind and translucency are `fn-render`'s ASSUMED values; no destruction particles / stump; low shrubs are only reachable with the knee sweep; the roughly 2 s of extra load is mostly CPU mip generation in `Renderer::create_static_material` (single threaded on the worker).

## Remaining gaps (honest)
* Pak mode is only partial: meshes and animation come from the paks; textures, `.mat` material slots, sky meshes, fonts and UI art still come from the asset roots (or the `fn-export --md5` cache, which needs `fn-export.exe` beside the game and a manifest, and produces `.mat.json` which the material loader does not read yet).
* Splash is drawn in the game window, not in a separate native splash window. Load-time errors show the in-window error page (and exit 1 on Esc); start-up, window, GPU and panic failures use the native message box (see Failure UX).
* Alt-tab / real keyboard + mouse + gamepad play were not exercised with real devices here; only their policy code (unit tests) and the self-test above.
* Renderer-side: AA and texture-quality settings are stored only; shadow-map size is on/off only; no main-menu 3D backdrop. (Props now use the static-prop path; see M2 below.)
* Exclusive fullscreen path (video modes, `pick_refresh`) is implemented and unit-tested at the policy level but the live test only switched to borderless fullscreen (to avoid changing the user's display mode).
* Window position / drag-resized size is not persisted (only the Settings screen values are saved, as in the old runtime). The windowed size is fitted to the monitor's real work area (`GetMonitorInfoW`).
* Audio: see "Audio hooks" below. Not done: in-world / lobby music (no cue is wired), which of the Morning / Day / Evening / Night ambience beds plays (Day is fixed), surface-dependent footsteps (the 1.8 data has none), voice chat; the hit / footstep / rock cues flagged A in `fn_audio::events::TABLE` are assumptions.

## Audio hooks (everything lives in `src/audio.rs`, `src/audio_test.rs`, `fn-game/src/audio_events.rs`, `fn-audio-sink`)
Shared-file hooks (each a few lines, marked `AUDIO HOOK`):
* `Cargo.toml`: deps `fn-audio` (device-output), `fn-audio-sink`, `fn-anim`, `fn-ueio` (footstep notifies are read from the clips in the paks).
* `main.rs` `run_main`: `audio::strip_cli(args)` (removes `--no-audio --audio --audio-test [wav] --audio-device-smoke` before `cli::parse`) and `audio::run_mode(&args)` (window-less modes); the `--help` text appends `audio::USAGE`.
* `app.rs` `App::new`: `AppBackend::new(path, audio::open_for_app(&opts, &source))` (was `NullAudio`); `on_mouse_button`: a press while the menu is open sends `SoundEvent::MenuClick`. (`GameplayAudio::update`, menu open / close and focus `set_suspended` were already wired.)
* `fn-game/src/lib.rs`: `pub mod audio_events;`.

Behaviour: the output device opens at once; a worker thread mounts the 1.8 paks (`--paks` / the run's paks / `FN_PAKS` / `FN_ROOT` / `Paks` beside the exe / the developer install), decodes the gameplay + UI cues, then the ambience loops (starts by itself when ready); a second worker reads the footstep AnimNotifies of the locomotion clips. No install or no device: `NullAudio` and one `[audio]` log line. Scripted / self-test runs are silent unless `--audio`. Settings > Audio sliders (Master, Music, Sound FX, Dialog, Voice Chat) and Quality reach the sink through `SinkHooks` / `AppBackend::apply_all` (live); focus loss / minimise mutes (no unfocused option exists in the settings table).
`fortnite-rs --audio-test out.wav` renders a scripted run offline (idle, jog, sprint + jump, crouch walk, 12 tree hits, 3 rock hits, probes) into `out.wav` (+ `out-dry.wav`, `out.report.txt`) and checks it against the game data; `--audio-device-smoke` plays 0.3 s of the pickaxe swing once at master 0.15. `cargo run -p fn-app --example audio_notifies` lists the AnimNotifies of every graph clip.

## Handoff (for the owner of `app.rs`, `ui.rs`, `startup.rs`, `loader.rs`, `cli.rs`)
1. `settings_note` is never printed: the file is now checked and its note logged by `main.rs` BEFORE `App::new` (`settings_guard::check_and_repair`; a corrupt `FortniteSettings.ini` is moved to `.corrupt` there, so your own `Settings::load` then sees "missing" and loads defaults). If you still want the app's own note in the log call `diag::log_settings_load(&report)` / `diag::settings_load_note(&report)` at the `Settings::load` site.
2. `init_window` creates the window at the raw saved size: prefer `platform::initial_client_size(w, h, el.primary_monitor().as_ref())` (repairs zero / tiny / > 8192 and fits the work area). `Gfx::new`/`resize` already clamp, so this is cosmetic.
3. `--live-test` (`live_sample`, `raw_dt`): the minimise probe is counted as a 1.1 s hitch (`4.12s:1110ms` in every run: it is the minimised time). Skip frames where the window was minimised / unfocused, or clamp `raw_dt`. Also fold `platform.last_audit` (`ok`, text = real clip rect vs client rect) into the `capture-at-start` / `menu-closed-state` checks; the `[capture]` lines are already in the log.
4. `open_menu` seeds the menu hover from `self.input.cursor`, which is the pointer position from BEFORE the capture; after a capture the OS pointer sits at the client centre (that is where `release` leaves it), so seed with `platform.client_center()` instead (the visible arrow and the hover otherwise disagree until the first mouse move).
5. `Gfx::take_error()` returns the first recorded wgpu error; poll it after the renderer is created in the loader (errors raised on the loader thread are reported at the next `acquire`, which is fine, but an early check gives a better message). `main.rs` shows a box for an exit with failure when `app.phase()` is not `Failed` (window / GPU creation failure) using the last `error:` line printed; keep `app::Phase::Failed` and the `error: ...` print in `fail()`.
6. Memory: `MenuSystem::new(ctx.fonts.clone())` in `ui.rs` duplicates every fontdue font (+59 MB heap); make the `Fonts` fields `Arc<fontdue::Font>` in `fn-ui/src/text.rs` and `clone()` shares them. Optional: drop the CPU RGBA of UI textures after upload (40 MB).
7. Renderer targets are re-created at every size change (`[slow] scene render ... 38-45 ms`); pre-creating them for the target size in the mode-switch path, or keeping the largest size, would remove the last hitch.
8. `fn-settings` test `catalog_json_matches_descriptor_table` currently fails on `audio.master_volume` (catalog says wired, table says stored-only): unrelated to this work, caused by the audio changes in flight. `audio.rs` has a baked developer path (`DEV_INSTALL = C:\Users\Brady\...`), same class as L1.


## Particles (PARTICLE HOOK)
`src/particles.rs`: the original Cascade systems of the harvest feedback. `fn-particles-export --paks <Paks> --props <assets\props> --out <assets\particles>` writes `<assets>/particles` (31 systems, 33 materials, 56 textures, 50 meshes; `FN_PARTICLES_DIR` overrides the folder); without it the harvest simply plays no particles. Hooks: `app.rs::start_loading` -> `particles::init` (proto -> `props.json` `destruction.death_particles`), `harvest_fx::feed` -> `particles::on_events` (`FxEvent::Broke` = the prop's DeathParticles at the prop, `FxEvent::Hit` / `WeakSpotHit` = `P_Melee_Impact_Default` at the hit point facing the player), `Scene::draw` -> `particles::submit` (tick by the frame's dt, `fn_render::ParticleFrame`), `run_report` -> `<script>-particles.txt` (one `spawn` / `done` line per system with the per-emitter spawn counts; `FNRT_PARTICLE_DEBUG=1` adds the first particle of every emitter every 20 frames). ASSUMED: every prop hit uses `ImpactPhysicalSurfaceEffects[4]` (the surface names are in the AES-encrypted ini), the ground is flat at y = 0, the death system is spawned unscaled at the prop's position with its yaw.
